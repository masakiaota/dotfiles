# Communication Memory

| 適用条件 | 望ましい対応 | 避ける対応 | 根拠 | 更新日 |
| --- | --- | --- | --- | --- |
| データモデルのレビューコメントを説明・起案するとき | まず主キーと解決先など直接関係する列の粒度を示し、それが成立しないドメイン前提を一つ述べて確認質問にする | 子テーブル・状態遷移・複数の仮説・解決案から説明を始めない | 訂正 | 2026-07-21 |
| 技術的な設計懸念へのレビューコメントを起案するとき | 「既存機能・事実 → 記録または設定すべき最小条件 → 解消できる問題」の順に、結論を直接述べる | 前置きで保存方式や選択肢を並べ、主張を疑問文や過度な留保に埋め込む | 訂正 | 2026-07-21 |
| 調査結果、更新差分、現在の状況を説明するとき | 冒頭の1〜3文で「何が変わったか、何が変わっていないか、それが何を意味するか」を答え、最初の段落だけで依頼への回答を成立させる。その後に根拠、詳細、追加の懸念を重要度順に示す | 実装詳細、評価、例外、追加の懸念から説明を始め、状況の骨格を後から示すことで、ユーザーに「つまりどういうことか」と質問し直させる | 訂正 | 2026-07-22 |
| GitHub PRのレビュー後に更新差分を説明するとき | 対象PRの先頭SHA、追加コミット、ファイル差分、コメントを確認する。コメントから別PRや別リポジトリへリンクされている場合は変更を分け、冒頭でそれぞれの変更有無を述べる | コメントの追加やリンク先の変更を、対象PRのファイル更新として説明する | 訂正 | 2026-07-22 |
| 提案の採用状況を説明するとき | 賛同、試作への反映、動作検証、正式文書への反映、物理スキーマへの反映、正式採用を区別し、確認できた段階だけを述べる | 賛同コメントや試作実装だけを根拠に「採用された」「全面的に採用された」と断定する | 訂正 | 2026-07-22 |
| 技術設計やレビュー論点を、ユーザーが質問を重ねながら段階的に確認しているとき | 直近の質問への結論を冒頭で答え、決定的な根拠と結論を変える留保だけを短く示して、そこで止める。確認済みの前提は保持し、次の論点は質問されるまで展開しない | 周辺の懸念、例外、将来課題、複数の解決案を先回りして並べる。長さや網羅性を分かりやすさとみなす | 訂正 | 2026-07-23 |
| 文書・スキーマ・処理フローを根拠に「できる／できない」「現状どうなるか」を説明するとき | 現行の名称と具体例を保ち、実際の処理順と実行主体を確認する。明記された事実、スキーマ上の表現可否、操作としての定義有無、推論を区別し、記載がなければ「未定義」と答える | 記載がないことを禁止・不可能と断定する。人とツール／バックエンドの責務を混同する。改善案や未提案の概念を現行仕様として説明する | 訂正 | 2026-07-23 |
| 明示された要件・制約と、周辺の一般論や代替可能性が併存するとき | 明示された要件・制約を判断基準として先に確定し、それに直接従う回答を示す。一般論や代替可能性は、結論を変える場合だけ区別して補足する | 例外や技術的可能性を同列に並べ、明示された要件の優先度や結論を曖昧にする | 訂正 | 2026-07-24 |
| 技術的な実装計画や実験計画を説明するとき | 最初に計画の重要な主軸を少数の観点へ整理し、観点ごとに何を実現・検証するのかを示す。その後、実装箇所、処理経路、テスト、例外を各観点へ紐づけ、冒頭だけで計画の骨格とユーザーが知るべき事項を把握できるようにする | ファイル、処理段階、テストケースを網羅的に列挙する一方で、重要度、観点、各項目が必要な理由を示さない。主軸を成立させる接続箇所を独立した論点のように並べる | 訂正 | 2026-07-24 |
